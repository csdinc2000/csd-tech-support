---
name: PTT RoIP bridge
description: The selected physical-radio interoperability boundary and its deployment constraint.
---

The selected optional physical-radio bridge is a fixed-address Twilio SIP Domain using authenticated SIP INVITEs and bidirectional PCMU/8000 Media Streams into the CSD-RoIP/1 Dispatch boundary. Browser-to-browser WebRTC PTT and server-enforced floor control are the core service; gateway readiness must never gate channel membership, revoke the browser floor, or mute browser operators. SIP credentials never enter browser responses.

Browser relay fallback uses Twilio Network Traversal Service tokens generated server-side from the existing Twilio account. Prefer these short-lived Twilio ICE credentials over a separate static TURN shared secret unless the project deliberately moves to another relay provider.

**Why:** Replit does not expose a raw SIP/RTP UDP edge, so Twilio terminates SIP and forwards media over an authenticated WebSocket. Twilio NTS avoids operating another relay service while keeping account credentials server-only. Physical-radio reachability is less reliable than the browser voice network and must degrade independently. The stream token and gateway state are process-local, so the bridge requires one always-on instance rather than a scaling deployment.

**How to apply:** Provision the SIP Domain credential mapping with the server-side RoIP provisioning command, configure compatible hardware for PCMU/8000 mono audio with VOX/RTP keying, and use a Reserved VM/always-on single production instance. The API artifact must claim the `/ws` service path as well as `/api`; otherwise browser PTT signaling and Twilio media streams fall into the frontend route. PTT and RoIP WebSocket servers sharing one HTTP server must use `noServer` mode with explicit pathname routing from upgrade listeners that ignore unrelated paths; attaching multiple path-scoped servers directly can make one reject the other's successful upgrade. Permit only one live PTT socket per authenticated operator, immediately clearing the superseded socket's floor; browser reconnect must discard every old peer before rejoining, and failed ICE should renegotiate rather than leave a dead peer cached. WebRTC audio transceivers negotiated before microphone permission produce streamless remote tracks, so receivers must construct a MediaStream from the track when the event has no stream; expose a user-gesture playback control when autoplay is blocked. Treat `lastSeen`, stream readiness, and disconnect state as the source of truth only for physical-radio health. Forward browser audio to RoIP only for authorized Dispatch floor holders while the transport is ready; bridge failures are non-fatal notices and never alter the browser floor.

Browser microphone tracks attached after the first SDP exchange require explicit `sendrecv` renegotiation when the operator receives the floor; `replaceTrack` alone is not reliable across browser/rejoin timing. Serialize incoming SDP/ICE processing, coalesce queued offers until signaling is stable, and use state-aware polite/impolite collision handling so overlapping microphone acquisition cannot leave both peers in `have-local-offer`.

**Why:** Two connected peers can otherwise show correct floor ownership while only one direction has an outbound RTP report. Concurrent late microphone acquisition also lets async WebSocket handlers process an answer and following offer out of order unless signaling work is serialized.
