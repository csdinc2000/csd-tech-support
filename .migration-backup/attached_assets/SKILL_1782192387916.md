# Replit Agent Hardening Prompt

A method for producing a paste-ready prompt that gets a coding agent to improve a messy,
partially-built app **surgically and safely**, instead of mass-rewriting it and breaking things.

## When this applies
The user has a real app that is partly built (dead links, half-wired integrations,
inconsistent UX, secrets in the wrong place) and wants a prompt/plan to make it solid.
The deliverable is **a prompt the user pastes into their agent**, not code you write yourself.

## Before writing anything — confirm these 5 facts
Ask via low-friction multiple-choice (not open prose) until you can answer all five. Without
them, the prompt will assume the wrong stack and the agent will introduce a second framework.

1. **Target agent** (Replit Agent / Cursor / Claude Code / generic) — changes format & how surgical to be.
2. **Stack** (frontend / backend / language) — so the prompt can *forbid* adding anything outside it.
3. **App state** (mostly built / disorganized / partial with dead links / rebuilding core) — sets how aggressive the audit is.
4. **Auth + DB** (Replit Auth, Supabase, custom, etc.) — drives the security phase.
5. **Key integration mechanism** (e.g. iframe+token vs REST/WS vs hyperlink) — drives the integration phase and the secret-handling rules.

If a sensitive integration is involved (RMM, payments, brokerage), **research its real auth
mechanism** before writing the security phase, so you name real secrets/endpoints, not invented ones.

## The non-negotiable shape of the prompt

### A. A ground-rules header that locks the agent down
Always include, near the top:
- **Stack lock**: name the exact stack; "do NOT add a second framework."
- **Surgical edits, not rewrites**: smallest change that fixes it; no "clean-up" rewrites of working modules without explicit approval.
- **Secrets server-side only**: nothing in the client bundle or `VITE_`-prefixed envs; browser talks only to the app's own backend, backend talks to third parties.
- **Phased & gated**: finish one phase, STOP, post a report, WAIT for explicit "go." Never chain phases.
- **No destructive ops without naming them first** (route/table/feature removal listed for approval).
- **Throughput priorities**: cache + batch fetching, low latency, propose SSE/webhook alternatives wherever naive polling would cause heavy API usage.

### B. Phase 0 is AUDIT ONLY — no code changes
This is the load-bearing part. The agent inventories before touching anything and ends by
proposing a phase order, then stops. Phase 0 should require:
- Route/nav inventory tagging each link WORKS / 404 / EMPTY STUB / RENDERS-BUT-BROKEN (these are the "dead links").
- Auth coverage map (which routes/pages are unprotected).
- **Secret-exposure scan of the client bundle** — highest-priority finding.
- Integration state (how it authenticates, where secrets live, does the browser call it directly, is data synced or live-fetched).
- Heaviest data-fetch paths (polling, refetch-on-render, N+1).
- UX/structure inconsistencies and degree of nav sprawl.

### C. Subsequent phases, each gated with STOP + report + await-go
A reliable default order (reorder to fit the audit):
1. **Navigation & routing integrity** — one nav config as source of truth; kill/stub/wire dead links; catch-all 404; router-level auth guards.
2. **Security hardening** (before any integration work) — move all secrets to server-side secret store; auth middleware on all API routes w/ public allowlist; rate limit + validate (zod) expensive/public endpoints; fail-fast env validation at boot; re-scan bundle to prove zero secrets.
3. **Integration done securely** — single backend proxy service holding credentials; browser calls only the app's own `/api/*`; **sync into own DB + cache** rather than live-fetch-everything; short-lived per-request tokens for embeds; timeout + circuit breaker so a slow third party never hangs the app.
4. **Data-layer efficiency** — query/cache layer (e.g. TanStack Query) with sane stale times; replace per-widget polling with SSE/WebSocket push or one batched poll; collapse N+1s; server-side caching for slow-changing reads.
5. **"Simple & organized" UX pass** — group sprawling nav into a few top-level domains; one shared layout shell; explicit loading/empty/error states everywhere; consistent primitives.
6. **Production readiness** — central typed error handling (no stack traces to client) + React error boundaries; structured logging with correlation id and secret redaction; `/healthz` checking deps; README of required secrets + integration config flags.

## Sparring-partner duties (do these, don't just transcribe)
- **Call out the "simple yet does everything" contradiction.** A 20+ surface nav and "simple/organized" pull opposite ways; recommend consolidation and cutting half-built features rather than finishing them.
- **Warn that a single mega-rewrite prompt is the main risk** — it burns the user's agent credits and breaks working flows. Push the audit-first gated structure.
- **Flag the crown-jewel secret** in any integration (e.g. a key that allows user impersonation) and insist it stays server-side, minted into short-lived scoped tokens.

## Worked reference: MeshCentral (RMM)
- `loginTokenKey` mints login tokens and allows **full user impersonation**; there is exactly **one per server** — treat as a crown jewel, server-side only.
- Embedding needs `AllowLoginToken: true` + `allowFraming: true`; the token rides in the URL as `?login=<token>`, is ~1h, and is copyable — so scope per device/session and log launches.
- Server-to-server control via the WebSocket/MeshCtrl API (ListDevices, ListDeviceGroups, RunCommand, devicepower) using a mesh superuser/login key.
- Proven shape (Tactical RMM): store mesh superuser + token server-side, periodically sync each agent's node ID into your own DB, use only a few mature features.

## Output
Deliver the prompt as a single markdown file the user can paste. Keep the ground-rules header
and Phase 0 audit verbatim-strict; tailor the later phases to the user's confirmed stack and integration.
